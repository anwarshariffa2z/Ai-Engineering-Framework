# Contributing

Contributions improve the framework when they are evidence-based, broadly applicable, and expressed as clear requirements or reusable practices.

## Before opening a change

1. Search existing documentation and open issues for overlapping guidance.
2. State the problem, affected lifecycle stage, intended audience, and expected outcome.
3. Distinguish a mandatory requirement (`MUST`), a recommended practice (`SHOULD`), and optional guidance (`MAY`).
4. Avoid vendor-specific prescriptions unless the guidance explains the portable principle and the vendor dependency is essential.

## Documentation changes

Documentation must be accurate, actionable, and self-contained. Include concrete decision criteria, ownership, and evidence where relevant. Do not add empty directories, skeletal templates, or unexplained TODOs. Link new material from the repository map or its parent document.

## Pull requests

Keep each pull request focused. Describe the problem, the proposed framework change, affected documents, and any adoption or migration implications. A maintainer will review changes for coherence, risk proportionality, and consistency with the principles in the README.

## Commit messages

Use an imperative summary with a clear scope, for example: `docs: define production evaluation evidence`.

## Code of conduct

Participation is governed by the [Code of Conduct](CODE_OF_CONDUCT.md).
